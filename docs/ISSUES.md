## I-3: TLS スケーリング行列がデータ分散ベース

**発見**: 2026-03-12

`tls.py` の `COLUMN_ONLY` モードで `T = diag(1/std(列))` を使用。std はデータのばらつき（信号+ノイズ）であり、ノイズレベルではない。高加振列（良い SNR）の信頼度が不当に低く扱われる。

**対応**: `ScalingMode.NOISE_BASED` を追加（diff ベースのノイズ推定）→ TODO 参照

## I-5: 120g 物体に対する 53g 推定（原因未特定）

**発見**: 2026-03-15

I-1, I-2, I-4 修正後、120g 物体の質量推定が一貫して ~53g (OLS raw)。

**棄却済み仮説**:
- F/T 再ゼロ化 (I-1): 修正済みだが 53g 持続
- リグレッサバグ (I-2): 慣性項のみ。修正済みだが 53g 持続
- q=0 汚染・同期不整合 (I-4): recording 内直接計算に変更し解消。1253 フレーム取得成功だが 53g 持続
- ツール重量姿勢バイアス: 理論予測では m_ols ≥ 120g（方向が逆）
- wrench 符号規約: 過去に検証済み（payload→sensor、反転不要）

**未検証**:
- OLS+bias: 1253 フレームで 249g。バイアスと質量列の共線性、バイアス推定値の物理的妥当性が未検証

## I-6: `/wrench` が `actual_TCP_force`（ペイロード補償 + 起動時ゼロ化済み）を使用

**発見**: 2026-03-16

UR ROS ドライバの `/wrench` トピックは RTDE 変数 `actual_TCP_force` を使用している（`hardware_interface.cpp:534`）。
この変数には以下の 2 つの補正が重畳されている:

1. **ペイロード補償**: Polyscope のペイロード設定 (mass, CoG) に基づく重力差し引き
2. **起動時ゼロ化**: ブレーキリリース時の F/T 読み取り値が定数オフセットとして自動差し引き

これにより:
- 慣性パラメータ同定に必要な絶対的な F/T 値が得られない
- バイアス列で吸収を試みても、ゼロ化オフセットと質量列の共線性で分離困難 (I-5 の根本原因)
- 起動ごとにゼロ化姿勢が異なるため、異なるセッション間でのデータ比較が不可能

**対応**: `ft_raw_wrench` (RTDE v5.9.0+, ゼロ化なし・補償なし) への移行を検討中。
ただし構造的プリロード (~25000) が含まれるため、無負荷状態でのプリロードキャリブレーションが必要。
→ 計画: `docs/plan_ft_preload_calibration.md` 参照

**追加発見 (2026-03-16)**:
- ft_raw_wrench の単位が UR 公式ドキュメントに記載されていない → **2026-03-17 に解決 (I-7)**
- プリロード値が時間ドリフトする（3 時間で Fy: ~27, Fz: ~23）→ 定数として扱うアプローチに限界
- 換算係数特定には既知質量での実測が必要 → **2026-03-17 に実測完了: 1 raw unit = 1 N**

**追加発見 (2026-03-17)**:
- Polyscope TCP/ペイロード設定を全てゼロにしても、`actual_TCP_force` に姿勢依存の定数オフセットが残る
- UR プログラム再起動時に自動ゼロ化が発生（local→remote 切替時を含む）
- マウント姿勢フロー（フランジ上向きで zero_ftsensor → グリッパ装着 → フランジ下向きへ移動）でも
  Fz が期待通り反転しない（上向き -13.6 N vs 下向き +5.0 N、期待 ±9.4 N）
- 連立方程式から m = 0.949 kg（秤 0.956 kg と整合）とオフセット C = -4.3 N を分離できる
- オフセット C は起動ごとに異なる（C = -10.4, -4.3 と変動）

## I-8: ft_raw_wrench の時間ドリフト

**発見**: 2026-03-16

同一条件（bare flange, ペイロード 0 lbs）で 3 回計測した結果、プリロード推定値が時間とともにドリフト。
- 3 時間: Fy で ~27, Fz で ~23 のドリフト
- 6 分以内: 安定（差分 < 0.1）
- 19 分: Fy で ~0.5 のドリフト（収束していない）
温度依存のストレインゲージドリフトと推定。

**追加発見 (2026-03-17)**:
- `actual_TCP_force` にも同等のドリフトが存在（ft_raw_wrench と感度 1:1 のため当然）
- 短期揺らぎ: 同一姿勢・同一ペイロードで 10 分間隔の差分計測にて ±5 N の変動を観測
- bare→loaded 差分計測 3 回: Fz diff = -8.79, -10.66, -8.97 N（秤実測 mg = 9.38 N）
- ドリフトは差分計測の bare/loaded 間の時間差にも影響し、差分値自体を汚染する

**UR フォーラム情報** (https://forum.universal-robots.com/t/drift-in-the-ur3e-f-t-sensor/41493):
- F/T センサ（Robotiq 製）は連続測定精度ではなく、定期的な `zero_ftsensor()` を前提に設計
- ドリフトの一貫性は保証されていない（仕様）

**対応**: 暖機時間の特定、または計測直前のプリロード取得を運用ルールとする。

## I-9: F/T センサの短期揺らぎ（±5 N）

**発見**: 2026-03-17

`check_ft_diff.py` による bare→loaded 差分計測を 10 分間隔で 3 回実施。ロボット姿勢は固定。

| Run | Fz diff [N] | m_est [kg] | bare raw Fz |
|-----|------------|------------|-------------|
| 1 | -8.79 | 0.897 | 25396.49 |
| 2 | -10.66 | 1.087 | 25400.76 |
| 3 | -8.97 | 0.916 | 25395.69 |

Run 1, 3 は整合（差 0.18 N）。Run 2 は bare 読み取り時にセンサが +4 N 高い値を示し、loaded 読み取りまでに戻ったため差分が拡大。

I-8 の長期ドリフト（温度依存）とは異なり、数分〜10 分スケールの不規則な揺らぎ。原因未特定（電気的ノイズ、メカニカルヒステリシス、温度勾配等の可能性）。

**影響**: 励起軌道（5 秒）中のドリフトは小さいが、bare/loaded のプリロードキャリブレーション精度に直接影響する。

**対応**: 特性評価が必要。複数回計測の平均化、または軌道直前直後のプリロード計測で補正。
